\heading{What could be misaligned?}
\textbf{Start delay.} Buffering alone can add several milliseconds. One 256-sample buffer at 48 kHz lasts \textbf{5.3 ms}; two last 10.7 ms. Converter, speaker and air delays are additional. This is an example, not measured UMC latency. Air adds about \textbf{3 ms per metre} in either setup.

\textbf{Trial variation.} How much the delay changes between trials is \textbf{unmeasured}. Preload the sequence and use wired audio. The moment the program calls ``play'' is not the sound's arrival time.

\textbf{Clock drift.} The interface-to-recorder mismatch is \textbf{unknown}. For scale, a hypothetical \textbf{100 ppm relative mismatch} means \textbf{6 ms per minute, or 0.36 seconds per hour}, if uncorrected. This is an illustration, not a prediction for this hardware.

\heading{How we align it}
Generate a reference alongside each tone on the spare output and record it with the brain data. Measure its offset to sound arrival with the microphone. Recording the mic only on the USB interface still leaves two clocks to align. Audio output is not TTL; recorder inputs determine the adapter. A compatible neural-recorder mic input would give a more direct acoustic reference.

Sound level still needs per-tone calibration at the ear.}

\heading{How much drift should we expect?}
\textbf{There is no measured Rice drift value yet.} NI lists 50 ppm timing accuracy, under its default typical-at-25\,$^\circ$C conditions. These calculations show clock-error scale before synchronization or correction:

The second row assumes a recorder specification we have \textbf{not confirmed}. Neither row is a guaranteed bound or a prediction of our alignment. A shared start trigger alone does not prevent drift.

\textbf{Prevent accumulating mismatch} by sharing a compatible clock, or use repeated recorded references to map the timelines. USB-6361 accepts a 10 MHz reference on PFI; recorder compatibility is open. Shared clocking still leaves acoustic delay and timing-measurement error.

\source{\buy{https://download.ni.com/support/manuals/374650c.pdf}{NI specifications, pp.1, 6, 14}; \buy{https://www.ni.com/en/support/documentation/supplemental/10/synchronization-explained.html}{NI synchronization}. Drift in milliseconds = relative error in ppm $\times$ elapsed seconds / 1,000.}

\heading{Which would I start with?}
\textbf{The basic setup, if tones below 20 kHz answer our question.} Test its alignment first. A proposed goal is \textbf{1 ms or less residual error after correction}; this is not achieved or guaranteed. Choose the expensive chain for the full SONIC frequency range. Arduino/FPGA can control playback and markers; sound arrival and drift still need measurement.

\source{\buy{https://doi.org/10.1101/2025.09.30.679683}{SONIC v1, Methods 6.2, p.11} used USB-6361, SA1, MF1 and PTP/10 MHz synchronization. It reports no measured acoustic-to-neural jitter or long-session drift. Rice's sedated sheep remain an adaptation of SONIC's awake, alert sheep. No setup here has been built or tested.}
